# Вход через Яндекс ID: отчёт за 8 октября 2026

Задача 1.1 плана релиза (`docs/roadmap.md`). Ветка `claude/gifted-golick-84d2e0`, в main не влита. Порядок работы: planner → реализация → editor → code-reviewer → qa.

## Что сделано

Вход через Яндекс ID поверх Supabase Auth, без провайдера в Supabase и без новых зависимостей (OAuth 2.0 на `fetch`).

- `src/lib/auth/yandex.ts`: ключи из `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET`, адрес страницы разрешений, обмен кода на токен (`POST oauth.yandex.ru/token`), чтение профиля (`login.yandex.ru/info`), разбор ответа через zod. Таймаут 8 с на каждый запрос. Токен Яндекса используется один раз и не хранится.
- `src/lib/auth/yandex-flow.ts`: cookie `tdd_yandex_state` (httpOnly, lax, 10 минут, только для `/auth/yandex`), роль и адрес возврата в `tdd_login_prefs`, сверка state через `timingSafeEqual`. Проверка `next` в `src/lib/auth/next-path.ts`: файл взят из ветки согласий без изменений, чтобы слился без конфликта.
- `GET /auth/yandex/start?role=&next=` и server action `startYandexLogin` (кнопка): начинают вход. Вошедшего пользователя маршрут уводит на его главную.
- `GET /auth/yandex/callback`: сверяет state, меняет код на токен, берёт `default_email` (считается подтверждённой, только если есть и в `emails`), имя из `real_name` или `display_name`. Затем service role выпускает одноразовый токен входа (`admin.generateLink`, как в режиме без письма) и отправляет браузер на существующий `/auth/callback?token_hash=…`, который ставит сессию и переносит роль и `next` из cookie в профиль. Финал входа один для письма и для Яндекса, поэтому при слиянии с веткой согласий (`claude/confident-thompson-26fac0`) проверка согласия на `/auth/callback` сама распространится на Яндекс.
- `src/components/shared/YandexLoginButton.tsx`: кнопка «Войти с Яндекс ID» внутри формы входа, `formNoValidate`, роль берёт из формы, почту и имя не требует и в адрес не кладёт (POST). Без ключей компонент не рисуется. Ошибки приходят в `/login?yandex=off|denied|state|email|failed` отдельно от `?error=`, чтобы не задевать словарь ошибок формы, который правит параллельная ветка.
- `src/app/login/page.tsx`: три строки (импорт, тип параметра, вставка компонента).
- `src/proxy.ts`: перенос `?code=` на `/auth/callback` больше не трогает пути `/auth/*`. Без этого proxy перехватывал callback Яндекса (нашёл planner).
- `.env.example`, `docs/deploy.md` (раздел «Яндекс ID»: регистрация приложения, Redirect URI, права, ключи на Vercel, ручная проверка через curl), `.claude/launch.json` (`dev-3002`).

Коммиты: `baa52b7` proxy, `c785eb8` helpers, `a137c00` routes, `85c8541` button, `e526ac6` launch config, `214491f` docs, `68742da` тексты после editor, `d62cb85` правки по ревью, `1e29054` правки по QA.

## Что проверено без ключей

Dev-сервер на 3002 с `.env.local` основного чекаута (режим `direct`), браузер на `[::1]` (на `localhost` и `127.0.0.1` cookie заняты сессиями других сессий).

- Без `YANDEX_*`: кнопки на `/login` нет, `/auth/yandex/start` и `/auth/yandex/callback` отвечают `307` на `/login?yandex=off` с сохранением роли и `next`.
- Старый вход `direct`: почта и имя → `/teach`, выход → `/`. Не менялся.
- `/?code=x` по-прежнему уходит на `/auth/callback?code=x`.

С фиктивными ключами (`YANDEX_CLIENT_ID=fake-client-id`, временно в `.env.local`):

- `start?role=teacher&next=/join/ABC` → `302` на `oauth.yandex.ru/authorize` с `redirect_uri=http://localhost:3002/auth/yandex/callback`, `scope=login:email login:info`, случайным `state`; две cookie с нужными атрибутами.
- `next=//evil.com` в cookie не попадает.
- Callback без cookie, с чужим state → `yandex=state`; `?error=access_denied` → `yandex=denied`; верный state и плохой код → настоящий ответ Яндекса `400 invalid_client`, в логе `[auth] yandex failed: token 400 invalid_client`, без кода и токена → `yandex=failed`. Cookie state удаляется при любом исходе.
- Кнопка в браузере: роль «Преподаватель», пустые почта и имя → POST через server action (в разметке `formNoValidate`, `formMethod="POST"`, почты в адресе нет) → страница входа Яндекса. Дальше с фиктивным client_id проверить нельзя.
- `npm run type-check`, `npm run lint` чистые.

Побочный эффект проверки: в проекте Supabase создан тестовый профиль `yandex-qa-teacher@example.com` (роль преподаватель, курсов нет).

## Что проверить нельзя и сценарий для Юлианы

Успешную ветку (обмен кода, профиль, сессия) можно пройти только с настоящими ключами. Код выпуска сессии тот же, что в рабочем режиме без письма.

После шагов из `docs/deploy.md` → «Яндекс ID» (локально: ключи в `.env.local`, `NEXT_PUBLIC_SITE_URL` не задан, redirect URI `http://localhost:3000/auth/yandex/callback` в приложении):

1. Новый пользователь. Открыть `/login?next=/join/КОД` (код любого опубликованного курса), роль «Студент», нажать «Войти с Яндекс ID», на экране Яндекса «Разрешить». Ожидание: вы на `/join/КОД`, в шапке имя из Яндекс ID. Проверка в Supabase → Table Editor → `profiles`: строка с почтой Яндекса, `role = student`, имя из Яндекса.
2. Существующий пользователь. Выйти, войти по почте (режим `direct`) с той же почтой Яндекса и именем «Другое имя», создать курс, выйти, войти через Яндекс. Ожидание: тот же профиль, курс на месте, имя осталось «Другое имя» (при входе через Яндекс имя существующего профиля не перезаписывается).
3. Роль. Выйти, на `/login` выбрать «Преподаватель», войти через Яндекс. Ожидание: `/teach`.
4. Повторный вход. Выйти и войти через Яндекс ещё раз. Ожидание: экран разрешений Яндекса второй раз не показывается, вход сразу.
5. Отмена. На экране Яндекса нажать «Отмена» или закрыть. Ожидание: `/login?yandex=denied` с текстом про отмену, обычная форма работает.
6. F5 на адресе callback после удачного входа. Ожидание: главная своей роли, без ошибки.
7. Истёкший state. Нажать кнопку, подождать 11 минут, нажать «Разрешить». Ожидание: `/login?yandex=state`.
8. Prod на Vercel: шаги 1 и 3 на `https://to-dual-daily.vercel.app`. Если Яндекс пишет `redirect_uri mismatch`, сверить `NEXT_PUBLIC_SITE_URL` и список Redirect URI.
9. Аккаунт Яндекса без почты (если найдётся) → `/login?yandex=email`.

Ручной обмен кода на токен через curl: `docs/deploy.md`, подраздел «Проверить обмен кода на токен вручную».

## Безопасность

- До `generateLink` нельзя дойти без совпадения state из cookie и ответа `login.yandex.ru` по токену, полученному за наш `client_secret`.
- `redirect_uri` собирается из `NEXT_PUBLIC_SITE_URL` (на проде) и в любом случае принимается Яндексом только из списка приложения.
- `next` только относительный путь: `//host`, обратные слэши и абсолютные адреса отбрасываются.
- Secret живёт в `process.env` на сервере, в клиентский код не импортируется (компонент кнопки серверный, проверяет только наличие ключей).
- В логах только код ошибки Яндекса и HTTP-статус, без `code`, токенов и почты.
- `token_hash` уходит в `Location` на `/auth/callback`: это та же одноразовая ссылка, что приходит в письме magic link, и живёт столько же.

## Слияние с `claude/confident-thompson-26fac0`

Сделано при слиянии в main 8 октября вечером: `startYandexLogin` читает чекбоксы согласия и кладёт их в `tdd_login_prefs`, без согласия отвечает `/login?error=consent`; `GET /auth/yandex/start` ведёт на `/login?role&next`, а не к Яндексу. Ниже исходные заметки.

- `src/app/login/page.tsx`: три строки, конфликт рядом с `<ConsentFields />` и типом `searchParams` решается вручную.
- После слияния обязательно: в `startYandexLogin` читать чекбоксы согласия, без `consent_processing` отвечать `/login?error=consent`, класть `consents` в `setLoginPrefs`, как делает `login`. `GET /auth/yandex/start` при этом должен вести на `/login?role&next`, а не сразу к Яндексу: по ссылке согласие отметить негде. Иначе аккаунт создаётся до согласия (152-ФЗ), хотя доступ и закроет редирект на `/consent` в `/auth/callback` той ветки. `login-prefs.ts` и `actions/auth.ts` там уже используют `safeNextPath`.
- `src/proxy.ts`: условие одно и то же в обеих ветках, конфликт тривиальный.

## Ревью (code-reviewer)

Блокеров нет: до `generateLink` не дойти без сверенного state, обмена кода за наш secret и ответа `login.yandex.ru`. Secret, код и токены в клиент, адрес и логи не попадают. `npm run type-check`, `npm run lint`, `npm run build` чистые, маршруты `/auth/yandex/*` в списке сборки.

Исправлено в `d62cb85`:
- Открытый редирект: `next=/%09/evil.com` проходил проверку «начинается с `/`, не с `//`», а парсер адресов убирает табуляцию и получает `//evil.com`. Теперь `next` разбирается через `new URL` и принимается только при совпадении origin (`src/lib/auth/next-path.ts`).
- Значение `?error=` от Яндекса писалось в лог как есть, до проверки state: любой мог вписать строки в лог Vercel. Теперь остаются только буквы, цифры, точка, дефис и подчёркивание, не больше 64 символов.
- После неудачной попытки cookie `tdd_login_prefs` жила ещё 30 минут и могла подставить роль и `next` следующему входу по ссылке из письма. Теперь удаляется при любой ошибке callback.

Оставлено как есть, с записью сюда:
- Согласия при слиянии с веткой `confident-thompson` (см. раздел «Слияние»).
- Кнопка Яндекса для вернувшегося преподавателя с радиокнопкой «Студент» по умолчанию переключит роль на студента, как и вход по почте. Вопрос для product.
- `token_hash` в `Location` на `/auth/callback`: риск тот же, что у ссылки из письма. Минус: если `verifyOtp` вдруг упадёт, пользователь увидит текст про устаревшую ссылку. Альтернатива на будущее: `verifyOtp` прямо в callback Яндекса, но тогда логику после входа придётся дублировать.
- Две вкладки: второй старт перезаписывает state, обе получают `yandex=state` и просьбу нажать ещё раз. Допустимо.
